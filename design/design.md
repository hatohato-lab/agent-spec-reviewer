# agent-spec-reviewer 設計メモ

この文書は「なぜこの設計にしたか」の記録。使い方は README を参照。

## 実証する設計パターン
**査読（レビュー）エージェント ＋「ラベル付き欠陥見本で検出力を測る」オラクル**。
出力が自然言語の判断（査読）になる処理を、わざと欠陥を仕込んだ見本で「正しく見つけられるか」で採点する。

## なぜこの方式を選んだか（他方式との比較）★この repo の肝
- 「仕様に適合しているか」の査読は、正解出力が一意でない（指摘の書き方は自由）。だから golden では測れない。
- そこで、欠陥が分かっている見本（正例＋既知欠陥）を用意し、査読が欠陥を検出し正例を通すかで測る。＝検出力(recall)と誤検出のなさを、ラベルで採点。採点は各見本の期待 issue 集合との完全一致で行い、見逃しだけでなく、期待外 issue の併記（過剰報告）や語彙外キーも FAIL にする。
- llm-judge と同系統（LLM の判断を、決定的なゲート＋ラベルで評価）。違いは「要約の質の点数化」でなく「定義の欠陥検出」。

## depth（粘りの深さ）と eval の関係 ★重要
- depth は実行時のダイヤル（quick / standard / deep）。deep は公式 docs を取得して突き合わせ、複数回見直す。
- eval は「standard で全欠陥を検出」を**床**にする。浅い査読（陳腐化を見逃す）は selftest で FAIL になる＝早く切り上げる査読を弾く。
- つまり「どこまで粘るか（depth）」と「最低どこまで満たすか（eval の床）」を分けて持つ。終わりはモデルの気分でなく eval が決める。

## なぜ信頼できるか（オラクル自己検証）
`--selftest` で、正しい査読は PASS、雑な査読（全部 conformant＝盲目／構造は見るが陳腐化を見逃す＝浅い／全欠陥キーを常に併記＝過剰報告）は FAIL になることを示す。

## 既知の限界
- eval が担保するのは「安定した構造ルール＋仕込んだ陳腐化の検出」まで。
- 「生 docs の最新差分への追従」は実行時（WebFetch）の機能で、ここは網羅評価しない（llm-judge と同じ正直な線引き）。
- issue キーの語彙は固定。新しい観点を増やすときは見本とラベルも増やす。
